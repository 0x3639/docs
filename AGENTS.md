# AGENTS.md

Guidance for AI agents and contributors working in this repository
(`0x3639/docs`, the Docusaurus site behind docs.0x3639.com).

## What this repo is

The developer documentation for Zenon's `go-zenon`. It has three layers:

1. **JSON-RPC reference** — `specs/openrpc/*.yaml` fragments, assembled into a
   single OpenRPC document `specs/openrpc.json` (served at `/openrpc.json`).
   Hand-authored from the pinned `go-zenon` source, verified against the godoc,
   with examples captured from a live node.
2. **Package reference** — `docs/reference/packages/*.md`, generated by
   `gomarkdoc` from the pinned `go-zenon` source. **Generated — never
   hand-edit.** They are gitignored and rebuilt by `npm run gen`.
3. **Guides** — hand-written MDX under `docs/`, with Go code injected from the
   compile-tested `examples/` module.

## The one invariant you must not break

`PINNED_GO_ZENON` pins `github.com/0x3639/go-zenon` at a SHA **on the
`docs/godoc` branch** — the branch that carries the godoc comments.
`go-zenon` `master` deliberately has **no** godoc comments.

→ **Never** repoint the pin at `master` or upstream `zenon-network`: the
generated package reference would come back empty. To advance the reference,
bump `ref=` in `PINNED_GO_ZENON` to a newer `docs/godoc` head, run
`npm run gen`, and commit the regenerated `specs/openrpc.json` and
`static/openrpc.json`. See `MAINTAINERS.md`.

The `examples/` Go module pins the same commit via a `replace` directive in
`examples/go.mod`; keep them in sync.

## Build, generate, test

```bash
npm ci                 # install
npm run gen            # fetch pinned go-zenon, gomarkdoc, assemble+validate openrpc
npm run build          # full Docusaurus build (must stay green)
npm start              # local dev server

npm run conformance    # replay spec examples against a live node, validate responses
cd examples && GOWORK=off go build ./... && GOWORK=off go vet ./...   # compile snippets
```

CI: `validate.yml` runs gen + build + compiles the examples module;
`conformance.yml` runs the conformance test on spec changes and weekly.

## How to make common changes

- **Add/fix an RPC method**: edit the namespace fragment in
  `specs/openrpc/<namespace>.yaml`, following the shape of the existing files.
  Verify the method against the pinned `go-zenon` source (handler godoc in
  `.build/go-zenon/rpc/api/...`); capture any example live from the node — never
  invent example values. Run `npm run gen` and `npm run conformance`.
- **Add a guide with code**: put compiling code in `examples/` between
  `// docs::start:<anchor>` / `// docs::end:<anchor>` markers, then reference it
  from MDX with `{@inject: examples/<file>#<anchor>}`. A missing file or anchor
  fails the build. `cd examples && go build ./...` must pass.
- **Grow the playground**: it reads `static/openrpc.json` via
  `src/data/openrpcMethods.js` — adding a method to the spec adds it to the
  playground automatically. Do not hand-maintain a method list.

## AI consumption

- `/openrpc.json` — the machine-readable JSON-RPC spec.
- `/llms.txt`, `/llms-full.txt` — generated index and full-text for LLMs.
- Each page's Markdown source is under `docs/`.

## Conventions

- Tool versions are pinned (Docusaurus, gomarkdoc, `@open-rpc/schema-utils-js`).
  Re-pin deliberately; don't float them with `^` ranges.
- Reference packages are generated — never hand-edit `docs/reference/packages/`.
- Every code snippet shown in a guide must come from the compile-tested
  `examples/` module.
